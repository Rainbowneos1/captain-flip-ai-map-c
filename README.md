### 1.1 最少需要几个文件？

**一个 html + 三个 js，放在同一个文件夹里就够了**（无子目录、无服务器、无构建、无网络）：

```
你的文件夹/
├─ index.html      ← 双击这个
├─ game.js         ← 引擎（必须先于下面两个被 <script> 载入，见下）
├─ weights.js      ← 量化权重，体积都在这里
└─ ai.js           ← 反量化 + 前向推理
```

* `index.html` 里只有三条相对路径的 `<script src>`，顺序为 `game.js → weights.js → ai.js`
  （`game.js` 挂 `window.CFS`，`weights.js` 挂 `window.CFS_MODEL`，`ai.js` 挂 `window.CFS_AI`；
  三者都在加载时只做定义、不互相调用，所以顺序其实只要保证都在 body 结束前即可）。
* **不能**用 ES module / `fetch`：`file://` 协议下浏览器会以 CORS 为由拒绝加载模块与 fetch，
  所以这里刻意全部用普通 `<script src>` 并把权重直接挂到 `window` 上——这正是"不依赖服务器"的前提。
* `export_weights.py` 与 `verify/` **不是运行必需的**，只是导出工具与验证脚本，删掉不影响游玩。
* 缺 `weights.js` 时页面**不会白屏**：它会照常渲染开局界面，但把提示改成
  「weights.js 未加载，AI 无法运行」并禁用「开始对局」按钮。
* **干净文件夹实测（闸门 5）：PASS** —— 把上述 4 个文件复制进一个空文件夹（另加一个测试驱动脚本），
  用 `file://` 打开、无头浏览器合成点击**完整打完一局**、页面 0 报错。命令：
  `powershell -NoProfile -ExecutionPolicy Bypass -File c-web\verify\run_clean_folder_test.ps1`
  （实测结果见 §5.5）。

## 2. 玩法与流程

1. **开局界面**：① 选择 **我先手**（你执玩家 1）或 **AI 先手**（你执玩家 2，AI 执玩家 1）；
   ② 地图固定为 **地图 C**（附 5 列预览：第 1 列藏宝图、第 2 列终局型 +6、第 3 列无奖励、
   第 4 列终局型 +4、第 5 列无奖励）；
   ③ 「📖 游戏规则」按钮弹出规则说明（含地图 C 的 5 列表格，可用 ✕ / 点遮罩 / Esc 关闭）；
   ④ 开始对局。
2. **对局界面**：左右两块棋盘（行 0 在最下，与原热座网页相同的摆法与图标）、列奖励图标行
   （地图 C：第 1 列 📜、第 2 列 🟰、第 4 列 🔢，无奖励的列显示 `·`；鼠标悬停给出该列完整规则）、
   分数、当前行动方高亮、底部对局记录。
3. **你的回合**：抽牌后二选一「保持朝上面放置 / 翻面查看（不可逆）」——选翻面会先把新的一面
   展示给你，再点「放置此方块」确认；然后点击任意一个高亮的列，方块落在该列最下面的空格；
   猴子效果会让你点一个高亮的相邻方块。**你只能看到朝上的一面**，另一面不可见。
4. **AI 的回合**：AI 抽牌、翻面、选列、翻猴子，每个决策点都有一行 `🤖 AI 决策：…`，
   写清它做了什么（翻了哪一面、放到第几列、该列的列奖励是什么——终局型列会明确写成
   「终局此列角色全同 +6（填满时不结算）」、翻哪个相邻格），
   并**至少停 1.2 秒**；若这次网络推理本身耗时超过 1.2 秒，就不再额外等待
   （实测推理平均 1.18 ms，所以正常情况下都是停满 1.2 秒）。
5. **结算**：角色效果、列奖励（地图 C：第 1 列填满即得藏宝图；第 2 / 第 4 列填满时**不结算**，
   留到终局）、终局计分（瞭望员/木匠/鹦鹉/水手 + 第 2 / 第 4 列的终局型列奖励）、
   炮手 ≥3 判负且记 0 分 —— 全部按现行规则实现；结束时给出胜负、终局分数、炮手数、完成列数，
   并提供「再来一局 / 重新选择先后手」。

### 2.1 地图 C 的规则（页面里的规则弹窗必须与此一致）

棋盘 5×5，只用到地图划出的 5 个竖直列；**行 0 = 最下**，方块总是落在该列**最下面的空格**。

| 列     | `rows`（自下而上）  | 格数  | 列奖励                                                                      |
| ----- | ------------- | --- | ------------------------------------------------------------------------ |
| 第 1 列 | 0, 1, 2       | 3   | 📜 `treasure`：**填满即获得藏宝图**                                               |
| 第 2 列 | 0, 1, 2       | 3   | 🟰 `end_if_same`（`score: 6`）：**只在终局结算** —— 此列已完成且全部角色相同 → **+6**         |
| 第 3 列 | 0, 1          | 2   | 无奖励                                                                      |
| 第 4 列 | 0, 1, 2, 3, 4 | 5   | 🔢 `end_if_all_distinct`（`score: 4`）：**只在终局结算** —— 此列已完成且角色互不相同 → **+4** |
| 第 5 列 | 0, 1          | 2   | 无奖励                                                                      |

> **三处容易看错、但确实是设计如此的地方**：
> 1. `end_if_same` / `end_if_all_distinct` 在**列被填满的那一刻什么都不做**（不得即时加分，
>    也不产生任何提示事件）；它们只在终局计分里结算。页面上的规则表与开局摘要都写明了这一点。
> 2. 终局型列奖励要求**该列已完成**（即 `finished[col] = true`，此列全部行都填满）；
>    未完成的列即使角色全同 / 互不相同也**不加分**。
> 3. 结算位置与 `cfs/engine.py:_compute_end_scores` 第 5 步完全一致：在
>    🚩瞭望员(+4) / 🪚木匠(+3) / 🦜鹦鹉(−1) / ⚓水手(+K²) **之后**、炮手计数**之前**，
>    **逐列一次加法**（`addScore` 的 0 下限截断依赖这个顺序）。

## 3. 权重压缩

**量化方案**：`per-group 对称 8bit`（`export_weights.py`）

* 只压 2D 权重矩阵；**沿输入维每 `group` 个数为一组**，每组独立求 `scale = max|w| / 127`，
  存 `round(w/scale)` 到 `[-127, 127]`。组内共用一把 scale ⇒ 组越小越精确、scale 开销越大。
* 偏置与所有 1D 参数保持 fp32（全部加起来 550 个数 ≈ 2 KB，压了没意义还伤精度）。
* 输出 `weights.js`：每个张量 = `{shape, g, sc:(base64 fp32 scales), d:(base64 int8)}`。
* **反量化在网页加载时一次性完成**（`ai.js: dequantize()` → `Float32Array`），
  推理全程 fp32，所以推理路径与 torch 的差别**只**来自量化本身。

### 3.1 体积与量化代价（地图 C，**交付检查点实测**）

> 下表全部由**交付检查点 `runs/c-r3/final.pt`**（iter 1000）产出。

| 项                      | 交付读数                                                                                                                    |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 参数量                    | **228,901**（`trunk.0` 256×599、`trunk.2` 256×256、4 个决策头 `[2, 5, 4, 25]`、`value`）                                         |
| fp32 原始大小              | **894.1 KB**                                                                                                            |
| 量化载荷（group 128）        | **232.4 KB**（int8 权重 + fp32 分组 scale + fp32 偏置）                                                                         |
| `weights.js`（base64 后） | **311.3 KB（318,776 字节）** → 压缩比 **2.87×**                                                                                |
| 相对重建误差                 | max **0.0039**（**每一个 2D 权重矩阵都是 0.0039** = 1/255 量级；闸门 3 的 dump 把 7 个张量逐张列出：`trunk.0/trunk.2/heads.0–3/value` 全是 0.0039） |

产出上面两项读数的命令：

```powershell

       --groups 128,64,32,16,8 --probe-games 500 --games 3000             # 一致率 + 头对头
```

**(a) 反事实动作一致率** = fp32 策略自己对局，在每个**多选**决策点上再问一次「量化网络会选什么」；
**(b) 头对头胜率** = 真正的验收：int8 策略 vs fp32 策略，交替坐先/后手，理想值 0.500。
两者与体积一起列在同一张表里（3000 局 / 组）：

| group       | 反事实一致率（多选决策点）                                          | int8 vs fp32（3000 局） | 载荷 KB     | `weights.js`（base64）KB |
| ----------- | ------------------------------------------------------ | -------------------- | --------- | ---------------------- |
| 8           | 99.54%                                                 | 0.5065 ± 0.009       | 336.8     | 449.0                  |
| 16          | 99.37%                                                 | 0.5055 ± 0.009       | 281.5     | 375.3                  |
| 32          | 99.12%                                                 | 0.5012 ± 0.009       | 253.3     | 337.7                  |
| 64          | 99.07%                                                 | 0.5032 ± 0.009       | 239.7     | 319.6                  |
| **128（采用）** | **98.84%**（22,597 / **22,862** 个多选决策点，另有 598 个单选决策点跳过） | **0.5030 ± 0.009**   | **232.4** | **309.9**              |

**结论：取最省的最小文件 —— `group = 128`。** 理由与地图 A / B 一致，而且是重新量出来的：

1. 把组从 128 缩到 8（体积 **+45%**）只把反事实一致率从 **98.84%** 抬到 99.54%；
2. **五个组在 3000 局头对头里全都测不出相对 fp32 的胜率损失** —— 0.5012–0.5065，
   全部落在 ±0.009 的 SE 之内（**与 0.500 全部不可区分**），而且没有单调趋势
   （最省的 128 反而最靠中（0.5030），最高的 0.5065 出现在体积最大的 8，两者差 0.0035 ≈ 0.4 SE）；
3. ⇒ 反量化的代价在本部署里**测不出来**，于是体积是唯一确定的收益项 ⇒ **取 128**。

> **历史参考（不是本部署的读数）**：地图 A 在 group 128 上的反事实一致率是 99.41%，
> 地图 B 是 98.86%（24,198 个多选决策点）。地图 C 的 **98.84%** 略低于两者 ——
> 说明地图 C 的网络对权重量化稍微更敏感一点 —— 但 3000 局头对头照样测不出差别，
> 这正好说明「一致率」只是过程指标，**头对头才是验收指标**。

> ❌ 衡量量化代价**绝不能**用"重放整局时的逐决策一致率"：第一个决策分歧之后，后面每一步
> 都在比较两个不同的局面，数字会虚高（地图 A 实测虚高到 98.80%，真实是 99.4–99.6%）。
> 一定要用**反事实一致率**（同一批状态）或**头对头胜率**。
> §3.1 表里的 98.84% 是反事实口径；闸门 3 里那句「int8 与 fp32 同选的比例 444/450 = 98.67%」
> 是同一口径但只有 10 局 / 450 个决策点的小样本，量级一致、精度以 22,862 个决策点的扫描为准。

## 4. 为什么引擎/特征要用 Python 那一套

AI 是照着 `cfs/encode.py` 的 599 维特征训练的，其中最后 19 维是**牌堆均值场后验**
（`P(背面=r | 正面=T)` 的 8 维、剩余朝上面期望 9 维、期望剩余总数 1 维）。网页里必须
**一模一样**地复现它，否则 AI 会看到它没见过的输入。因此：

* `game.js` 里的 `Game` 用**生成器**复刻 `cfs/engine.py` 的协程结构（鹦鹉嵌套回合、
  猴子连锁翻面都靠 `yield`），决策点协议（flip / col / monkey）与 Python 完全一致；
* `MeanFieldBelief` 是 `cfs/belief.py` 的均值场方案的逐行移植（软移除台账 + 完整对修正）；
* `BeliefDriver` 只从**公共视图序列**推出信念事件（同样不读牌堆），保证没有隐藏信息泄漏；
  注意它必须拿到**本地图的列定义**（`game.columns`）才能把「列动作」还原成落点行 ——
  地图 C 传错成地图 A/B 的列定义会**静默**算错信念特征（见 §7.2）；
* 列几何与列奖励全部来自 `game.js` 顶部唯一的 `MAP_C` 常量，与规则保真源
  （项目根的 `index.html` L129-L138）以及训练权威 `cfs/engine.py: MAPS["C"]` 逐字段一致；
* 结局与计分按**现行规则**（`boomRule="lose"`：炮手 ≥3 判负且该方记 0 分）。

## 6. 已知取舍

* **只支持地图 C**（按需求）。引擎里保留了其它地图的列奖励分支（`first_complete`、
  `score_per_completed_cols`、`if_same_then` …），但地图 E 的 `flip_tile`、地图 G 的囚徒区
  遇到会**显式抛错**（错误信息说明它们属于地图 G、不在本部署范围内），而不是静默出错。
* **`runScript` 只接受 `map: 'C'`**：本页引擎常量已固定为地图 C，接受别的地图标签等于用地图 C
  的列去跑一局标签为别的地图的对局 —— 那种静默错误比直接抛错难查得多，所以直接拒绝。
* **量化是有损的（实测代价，可接受）**：group 128 下**反事实一致率 98.84%**
  （22,597 / 22,862 个多选决策点），即约 **1.16%** 的决策与 fp32 网络不同；
  但 **3000 局 int8 vs fp32 头对头 = 0.5030 ± 0.009（与 0.500 不可区分，|z| ≈ 0.3）**
  ⇒ 量化造成的胜率损失**测不出来**。缩小组（64/32/16/8）能把一致率抬到 99.07–99.54%，
  代价是体积 +3%～+45%，而头对头读数（0.5012–0.5065）仍全部落在噪声里 ——
  所以选最小文件 `group = 128`。完整矩阵见 §3.1。
  （对比：地图 A 是 99.41%、地图 B 是 98.86%；地图 C 的一致性略低，但结论相同。）
* **交付数字与检查点绑定**：§2.2 / §3.1 / §5.3 / §5.4 / §5.5 / §6 的所有读数都是
  「`runs/c-r3/final.pt`（iter 1000）+ group 128」这一组实测的。换检查点或换 group
  必须**重新导出 + 重跑闸门 3**（`py_trace.json` 按当时的权重复算），不能沿用旧的绿。
  注意 `export_weights.py` / `quant_sweep.py` 的 `--ckpt` **默认值仍指向第 1 轮的
  `runs/c-r1/final.pt`**，所以重导出时务必显式传 `--ckpt runs/c-r3/final.pt`（§3.2）。
* **地图 C 的终局型列奖励极易写错**：填满时不得即时加分、未完成的列不得加分、结算位置必须在
  水手之后炮手之前、且逐列一次加法（0 下限截断依赖顺序）。这四点由闸门 2（对拍 digest 的
  `finalScores`）、闸门 3（端到端 digest）与 §5.7 的独立验证共同锁住。
* 牌堆耗尽时按原规则**重建整副新牌堆**（`index.html` 行为）；`jsref` 参考引擎为了对拍
  不重建而是报错，这是两边**已知且有意**的差异（对拍脚本会给足 300 张牌）。
* AI 用确定性 argmax（与训练评估口径一致），不复现采样带来的多样性。

## 7. 修复记录

### 7.1 对局记录的归属错位（沿用地图 A 的修复，本部署已包含）

**现象**：日志里「你抽到…」其实是 AI 抽的，「AI 抽到…」其实是你抽的。

**根因**：引擎的一次 `game.step()` 并不只做"当前玩家的这一步"——它在结束当前回合后
**会继续一路推进到下一位玩家的第一个决策点**（决策点协议就是这么设计的），于是同一批事件里
同时包含当前玩家本步的事件与**下一位玩家的 `draw`**；终局计分更会一次性抛出双方的计分事件。
旧代码按"刚刚是谁在行动"给整批事件打标签，于是全错。

**修复**：归属改为**按事件自带的玩家** `ev.p`。由 `verify/check_log_attribution.mjs` 锁住。

### 7.2 地图 C 移植期修掉的（本次）

### 7.3 移植期的两条操作纪律（血泪）

* **不要用 PowerShell 的 `Get-Content`/`Set-Content` 管道改写 UTF-8 源文件**。5.1 默认按 ANSI(GBK)
  解码，中文被错配后其尾字节会与紧跟的 `\r` 组成非法序列、**连换行一起吃掉**，文件会静默损坏
  （地图 B 时期在 `game.js` 上踩到一次，靠"从参考部署重拷 + 重做编辑"恢复）。
  需要批量替换就写一个 **Python** 一次性脚本，并对每处替换先断言 `count(old) == 1`；
  或者用 **UTF-8 感知的编辑器工具**逐处替换。
* **`.ps1` 一律 ASCII-only**；中文清单文本交给 Python 写。
  `c-web/verify/*.ps1` 经逐字节检查**全部是 ASCII-only**。
